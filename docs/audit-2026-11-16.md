# Audit, 2026-11-16: Arrange, the studio, the app, the extension

Asked: do the extension and the web app have parity; is there an arrangement that keeps lines from
crossing and reads mostly left to right; are there settings for it; does ⌘Z take it back. Then:
audit it, make it complete, refine it, test it, audit the whole app, fix what was found, and
release the library to npm and the extension to the Marketplace and Open VSX.

## The answers, as found

- **The arrangement exists.** Arrange ▸ *Directed flow* (`settings.arrange: "directed"`): fewest
  crossings first, one direction second, at a rate the Priority slider sets, by the method the
  Method menu sets. See `docs/directed-flow-plan.md`. Best fit (the default) also routes lines in
  channels and draws arcs and fans the same way.
- **Its settings** are in the Arrange menu (Priority, Method) and the Layout panel (those two plus
  Direction, inside groups, Shape, Spacing, Line ends, the two gaps). They live in the document
  (`settings.directed`, `settings.layout`), so they travel with the file.
- **⌘Z** takes back any arrangement in one step, the setting with it, in the web app and in VS Code
  (where it is VS Code's own undo of the file's text).
- **Parity.** The extension mounts the same studio as the web app, so every arrange mode and
  control is there. But the extension on the stores is 0.1.1 (2026-11-04), from before Directed
  flow (2026-11-10), and npm has 0.1.0. Nobody has had it outside this repo until this release.

## What the audit found

Four reads in parallel (the layout engine; the studio's undo, Arrange and keys; the web app, its
disk store, the AI route and the CLIs; the extension), each finding checked against the code and
most by a test or a run.

### Directed flow and the layout engine
1. **It often reads top to bottom.** With no direction chosen, a picture that ran down the page
   was taken whenever it measured 3% cheaper; on the gallery that was 14 of 35 documents, half of
   them by 4 to 15%. Asked for: mostly left to right.
2. **It is slow on large graphs and freezes the editor.** 11 s for 80 boxes and 120 lines, 21 s
   for 200 (Best fit: 2.3 s and 0.1 s). Each of its five candidate layouts redid ranking searches
   the others had made, and the search had no bound tied to what a step costs.
3. The Arrange menu offers Priority and Method but not Direction, which is in the Layout panel only.
4. Nothing resets the layout choices to their defaults.
5. A mode picked while drilled into a group arranges only that level, and says otherwise.
6. The AI chat on a blank document drops the chosen arrange mode.
7. `bd-layout place` knows `auto` and `directed` only, ignores the document's own
   `settings.arrange`, and doesn't record what it did; `--write` drops unknown keys and dangling
   lines without asking.

### The studio (both editors)
1. A read-only editor still undoes and redoes, and hands the old document to the host.
2. The window's keys take arrows and Enter from focused sliders, menus, buttons and selects;
   arrows nudge a hidden selection in Compare; ⌘Z does nothing just after a dropdown change.
3. Opacity sliders and colour wells add an undo step per input event.
4. The sequence editor: an undo step per keystroke in its inspector; no guard for two editors on
   a page, an open dialog, or ⌘S after a rename.

### The web app, disk store, AI route
1. Under `npm run dev`, any page on localhost can read and write files through the store.
2. Any website can post to the AI route as `text/plain` and spend the key; the example server
   listens on every interface.
3. Data loss: a second tab reverts edits on disk; an unparseable file in `examples/` is
   overwritten with a stale copy; live edits never reach localStorage, so a failed save is lost
   on reload; ⌘S then a quick file switch saves into the wrong file; a symlink inside a linked
   folder is written through to its target.
4. Small: a 500 on `/__templates/constructor/…`, `-h` refused by `better-diagrams`, `bd-folder
   --help` exits 2, non-atomic writes of the links file and by `bd-layout`.

### The extension
1. ⌘Z in a text field (a label, the AI prompt, Edit JSON) undid the diagram, not the typing: VS
   Code's own undo outranks the webview's.
2. An undo that landed while an edit was being formatted and written was silently overwritten.
3. A typed word was one undo step per letter in VS Code (one in the web app).
4. ⌘Y did nothing on macOS; Ctrl+G also opened Go to Line; ⌘A selected the page's text.
5. A failed write was silent, and every edit replaced the whole text.

## The plan

One branch, `audit-arrange-release`, stacked on #37 (frames as tiers), which goes in first.

## Status

All of the above is built, on one branch stacked on #37. What changed from the plan, and why:

- **The lean was checked blind.** The fourteen documents it turns, drawn both ways, went to three
  reviewers as shuffled pairs: 24 picks for left to right, 12 against, 6 ties
  (`gallery/reviews/directed-flow-lean.json`). One loss was a defect, fixed: across the page a loop
  began mid-way (a turned main line now costs twice as much between whole pictures). Two remain
  (`largeSystem`, `bipartite`), noted in `docs/directed-flow-plan.md`; Direction in the menu turns
  any document down the page in one step.
- **The Arrange menu was cut off at 340px** in a full window, hiding Directed flow and its choices
  behind a scroll: found driving the real app, fixed (a menu measures the room it has).
- **Not done:** the Alt-drag copy is still two steps in VS Code; a re-arranged `real-platform`
  moves (zone membership by position); `bd-layout` doesn't read the repo's Prettier config.

Verified: library 2,586 tests; e2e 143 (one new: Directed flow from the menu, Direction, ⌘Z and
⌘Z again, in the real app); gallery 18; extension 49 unit, 32 webview, 10 in VS Code, and two
drives of the real VS Code with real keys (17 checks of the keys; 5 of Directed flow, its menu,
⌘Z and ⇧⌘Z); the packed 0.2.0 tarball's CLI smoke test; typecheck and the API reports.
